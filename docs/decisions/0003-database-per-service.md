# ADR-0003. База данных на сервис в одном инстансе PostgreSQL

**Статус:** принято, 17.09.2026

## Контекст

Три сервиса с состоянием. Нужно защитить границы (иначе кто-нибудь сделает JOIN между
планом и фактом, и микросервисы кончатся), но нельзя раздувать инфраструктуру: на демо
поднимается всё на одной машине.

## Решение

Один контейнер PostgreSQL 16, **три базы и три роли**: `plandb/plan_user`,
`sitedb/site_user`, `analysisdb/analysis_user`. Роль имеет права только на свою базу.
Межсервисные ссылки — по UUID, **без внешних ключей**. Миграции — Alembic, у каждого
сервиса свои.

## Последствия

**Хорошо:** границу защищает СУБД, а не договорённость: чужой JOIN физически не выполнится.
Контейнер один, памяти и времени на запуск минимум. Разнести базы по инстансам позже —
замена одной строки DSN.

**Плохо:** нет ссылочной целостности между сервисами — «висячий» `object_id` возможен.
Компенсируется проверкой при записи и тем, что удаление объекта переводит его в `ARCHIVED`,
а не удаляет. Нет распределённых транзакций — их и не должно быть: каждый сценарий
пишет в одну базу, остальное — идемпотентные пересчёты.

## Альтернативы

- **Одна общая база на всех.** Быстро и привычно, но через день кто-нибудь сделает JOIN,
  и заявленная архитектура перестанет быть правдой.
- **Схема на сервис в одной базе.** Слабее изолирует, при этом не проще.
- **Три отдельных контейнера Postgres.** Честнее, но три инстанса ради демо на ноутбуке —
  лишние полтора гигабайта памяти без единого нового свойства.
