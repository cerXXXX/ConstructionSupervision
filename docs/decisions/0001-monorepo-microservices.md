# ADR-0001. Монорепозиторий и микросервисы

**Статус:** принято, 17.09.2026

## Контекст

Система состоит из частей с принципиально разными зависимостями и темпом изменений:
компьютерное зрение (torch, ~2 ГБ образ), нормативные расчёты (чистый Python),
работа с изображениями, методика сверки, LLM, интерфейс. Команда работает четырьмя
параллельными треками, срок — полторы недели. Заказчику продукт нужен как **модуль
его системы**, то есть с внятными границами и API.

## Решение

Один репозиторий, несколько сервисов, каждый — отдельный Docker-образ. Запуск —
`docker compose`. Общение — только по HTTP REST.

Монорепозиторий, потому что: один PR меняет контракт и обе стороны сразу; общие правила,
линтеры и CI в одном месте; нет ада с версионированием внутренних библиотек; на хакатоне
скорость согласования важнее независимости релизов.

Микросервисы, потому что: несовместимые зависимости (torch vs. чистый FastAPI); разный
профиль нагрузки (CV масштабируется репликами, план — нет); падение LLM или CV не должно
ронять систему; заказчик прямо оценивает архитектуру и возможность встроить части в свою ИС.

## Последствия

**Хорошо:** параллельная работа без конфликтов; тяжёлые зависимости изолированы;
любой сервис можно отдать заказчику отдельно; отказ одной части деградирует систему,
а не убивает.

**Плохо:** больше инфраструктурного кода (7 Dockerfile, 3 набора миграций); сквозная
отладка сложнее — компенсируется `X-Request-Id` в каждом логе; риск переусложнить —
компенсируется правилом «новый сервис только через ADR».

## Альтернативы

- **Монолит FastAPI.** Быстрее на старте, но torch тянется в каждый процесс, нельзя
  масштабировать CV отдельно, и архитектурный критерий оценки закрывается хуже.
- **Полирепозиторий.** Независимые релизы не нужны за полторы недели, а издержки
  на синхронизацию контрактов — сразу.
- **Serverless / очередь функций.** Требует инфраструктуры, которой у заказчика на демо нет.
