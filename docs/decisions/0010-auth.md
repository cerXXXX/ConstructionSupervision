# ADR-0010. Аутентификация по API-ключу с точкой расширения на SSO

**Статус:** принято, 17.09.2026

## Контекст

Продукт для города: в эксплуатации потребуется полноценная аутентификация, роли
(инспектор, подрядчик, руководитель) и аудит. На хакатоне за полторы недели собственная
система пользователей съест время, которое нужно методике, и не добавит ни одного балла
по критериям оценки.

## Решение

- Все `/api/v1/**` требуют заголовок `X-API-Key`. Исключения: `/health`, `/health/ready`,
  `/docs`, `/openapi.json`.
- Ключ один на установку, задаётся переменной `API_KEY`, проверяется общей зависимостью
  из `py-common` — одинаково во всех сервисах.
- Сервисы во внутренней сети compose используют тот же ключ: своего доверия «по сети» нет.
- Аудит действий оператора (правка плана, вердикт по отклонению) пишется с полем `author`
  из заголовка `X-Actor` — заготовка под будущие учётные записи.
- **Точка расширения:** проверка ключа вынесена в одну зависимость. Переход на OIDC
  (SSO Москвы, Keycloak) = замена её реализации и добавление проверки токена в gateway.
  Доменная логика не меняется.

## Последствия

**Хорошо:** система не открыта наружу; интеграция для заказчика — один заголовок;
время сэкономлено для методики.

**Плохо:** нет ролей и разграничения прав; компрометация ключа даёт полный доступ.
Оба ограничения **явно заявлены** в документации и на слайде «дальнейшее развитие» —
это честнее, чем имитация безопасности.

## Альтернативы

- **Своя система пользователей с JWT и ролями.** Два-три дня работы и ноль баллов
  по критериям; роли всё равно придётся переделывать под модель доступа заказчика.
- **Keycloak в compose.** Плюс тяжёлый контейнер и настройка realm ради демо.
- **Совсем без аутентификации.** Неприемлемо для городского заказчика даже в прототипе.
