# Доска задач

[roadmap.md](roadmap.md) говорит, **когда** и **что за день**; доска говорит, **какая именно
задача сейчас взята и кем**. Ячейка роадмапа вроде «D3–D6, дедупликация отклонений» — это день
работы, а не задача, которую можно выдать человеку или агенту. Разложить её на задачи — работа
владельца трека, и результат лежит здесь.

Доска — обычный файл в git: она греппится, видна в диффе и не требует ни сервера, ни аккаунтов.
Когда задач станет больше, чем помещается в голову, она за десять минут переезжает в GitHub
Issues — идентификаторы задач останутся теми же.

---

## 1. Как устроена запись

```markdown
- [~] `B-04` site-service: приём снимка, MinIO, дедупликация по sha256
      спец: services/site-service/README.md §3 · блокирует B-05 · взял: Иван
```

| Знак | Значение |
| :--- | :--- |
| `[ ]` | не начата, можно брать |
| `[~]` | в работе; во второй строке обязателен `взял: <имя>` |
| `[x]` | закрыта по DoD ([AGENTS.md, раздел 5](../AGENTS.md#5-рабочий-цикл)) и влита в `main` |

Вторая строка необязательна, но в ней живёт всё, что экономит время исполнителю:
`спец:` — где написано, что именно делать (README сервиса, раздел методики, пункт ТЗ);
`блокирует:` / `ждёт:` — связи между задачами; `взял:` — кто ведёт.

## 2. Правила доски

1. **Задачу назначает человек.** Агент не выбирает себе задачу сам — иначе два агента возьмут
   одну и вы получите два конфликтующих решения одного и того же.
2. **Одна задача — один модуль или один эндпоинт.** Проверяемая эвристика: если дифф больше
   ~300 строк, задача была слишком крупной. На «реализуй site-service» агент выдаст две тысячи
   строк, которые никто не прочитает.
3. **Каждый трек правит только свой раздел.** Так четверо одновременно меняют доску без
   конфликтов слияния.
4. **Взял — сразу поставь `[~]` и своё имя**, отдельным коммитом в `docs/`. Это дешевле, чем
   выяснять вечером, кто что делал.
5. **`[x]` ставит тот, кто закрыл задачу, и только после того, как PR влит.** Не «код написан»,
   а весь чек-лист DoD.
6. **Утром ячейка роадмапа на сегодня превращается в задачи здесь.** Это и есть вся планёрка:
   десять минут, каждый берёт 2–4 задачи.

Ветка и PR — по [AGENTS.md, раздел 11](../AGENTS.md#11-git): `feat/<service>-<кратко>`,
номер задачи в описании PR (шаблон подставит поле `Задача`).

## 3. Треки и владельцы

| Трек | Зона | Сервисы | Владелец |
| :--- | :--- | :--- | :--- |
| **A** | План и нормативы | `pos-engine`, `plan-service` | не назначен |
| **B** | Площадка и зрение | `site-service`, `vision-service`, `ml/` | не назначен |
| **C** | Методика | `analysis-service`, `report-service` | не назначен |
| **D** | Интерфейс и инфраструктура | `apps/web`, `gateway`, `scripts/`, CI | не назначен |

Впишите имена до первой задачи: владелец трека отвечает за то, что его раздел доски не пуст и
не врёт.

# Текущий рубеж: T0 — скелет, к 20.09

Условие T0: `docker compose up` поднимает весь стек, все сервисы отвечают `/health/ready`,
план генерируется из названия объекта, снимки загружаются и проходят через CV, анализ выдаёт
D1/D2, UI показывает объект и ленту отклонений. **Пока T0 не поднимается целиком, задачи T1
не берутся** — это правило роадмапа, и доска его не обходит.
