# Сопроводительная документация проекта «СтройКонтроль»

> **Проект:** Автоматизированный сервис поиска нарушений на строительных площадках Москвы  
> **Конкурс:** «Лидеры цифровой трансформации» (ЛЦТ) 2026, кейс 07  
> **Заказчик:** Департамент градостроительной политики города Москвы  
> **Целевая ветка репозитория:** `main`

---

## 1. Модель данных

Хранение данных организовано по архитектурному паттерну **Database-per-Service**: каждый микросервис с состоянием владеет собственной физически изолированной базой данных в СУБД PostgreSQL 16. Прямые межсервисные SQL-запросы и внешние ключи (Foreign Keys) между базами исключены; обмен данными между сервисами осуществляется исключительно по протоколу HTTP REST API с передачей сквозных идентификаторов в формате UUIDv4.

### 1.1. Базы данных микросервисов

| Сервис | База данных | Назначение и состав хранимых сущностей |
| :--- | :--- | :--- |
| **Сервис плана** (`plan-service`) | `plandb` | **Нормативный план и правила:** строительные объекты (`object`), календарные графики производства работ (`stage`), справочник видов работ (`work_type`), технологические правила соответствия «этап → техника» (`stage_rule`), рабочий производственный календарь (`work_calendar`). |
| **Сервис площадки** (`site-service`) | `sitedb` | **Физическая площадка и наблюдения:** реестр стационарных камер (`camera`), разметка полигональных участков и опасных зон (`zone`), каталог принятых снимков (`image`), результаты распознавания техники на кадрах (`detection`), 30-минутные окна агрегации наблюдений (`observation_window`), статус видимости зон (`area_visibility`), оценки визуальной стадии объекта (`stage_observation`). |
| **Сервис анализа** (`analysis-service`) | `analysisdb` | **Сверка план-факт и инциденты:** прогоны план-факт анализа (`analysis_run`), журнал зафиксированных отклонений и нарушений (`deviation`), реестр настраиваемых правил отклонений (`deviation_rule`), фактические показатели прогресса и прогноз завершения этапов (`stage_fact`), ежедневные метрики активности (`daily_activity`), учет использования техники (`equipment_usage`), сгенерированные аналитические PDF-отчеты (`report`). |
| **Объектное хранилище** (`gateway` / SeaweedFS) | S3 Buckets | **Бинарные медиафайлы:** оригиналы и оптимизированные снимки с камер (бакет `images`), сформированные PDF-отчеты с подтверждающими материалами (бакет `reports`). |

### 1.2. Хранение информации о строительной технике

Учет техники в системе охватывает весь жизненный цикл — от сырой детекции на кадре до расчета эффективного рабочего времени:

1. **Единый классификатор техники (`packages/contracts/equipment_classes.yaml`):**  
   Централизованный файл-контракт для всех сервисов системы. Содержит 16 классов строительной техники (8 базовых классов технического задания + 8 дополнительных классов), текстовые англоязычные промпты для открытого словаря детектора, признак транзитности (`transient`), признак работы без перемещения (`works_in_place`), а также таблицу соответствия меток внешних датасетов (`aliases`).

2. **Сырые детекции на снимках (`sitedb.detection`):**  
   Каждая обнаруженная единица техники сохраняется со следующими параметрами:

    - `image_id` — идентификатор снимка;
    - `equipment_class` — нормализованный код класса техники;
    - `bbox` — нормализованные координаты ограничивающей рамки `[y_min, x_min, y_max, x_max]` в диапазоне от 0.0 до 1.0;
    - `bottom_center` — точка контакта машины с землей `[x, y]` для точной геометрической привязки к полигонам зон;
    - `zone_id` — идентификатор полигона зоны, в границы которого попала точка контакта;
    - `confidence` — степень уверенности детектора (число от 0.0 до 1.0);
    - `model_version` — имя и версия модели нейросети, выполнившей распознавание.

3. **Агрегированный учет работы и простоев (`analysisdb.equipment_usage`):**  
   В рамках 30-минутных окон наблюдений (`observation_window`) фиксируется статус каждой машины:

    - `WORKING` — активная работа (перемещение точки контакта свыше порога или стационарная работа кранов и бетононасосов на пятне застройки);
    - `IDLE` — необоснованный простой (техника неподвижна несколько окон подряд);
    - `OUT_OF_ZONE` — нахождение машины за пределами целевого участка производства работ.

### 1.3. Хранение информации об этапах работ

Система поддерживает 4 типа объектов капитального строительства (`packages/contracts/enums.yaml`):

- **Монолитное домостроение** (`RESIDENTIAL_MONOLITH`) — жилые монолитные здания;
- **Панельное домостроение** (`RESIDENTIAL_PANEL`) — жилые панельные здания;
- **Общественные здания** (`PUBLIC_BUILDING`) — школы, детские сады, поликлиники, административные комплексы;
- **Дорожное строительство и благоустройство** (`ROAD`) — автомобильные дороги и объекты улично-дорожной сети.

Структура данных планирования включает:

1. **Календарный график СМР (`plandb.stage`):**  
   Каждая позиция графика включает плановые даты старта и окончания (`plan_start`, `plan_end`), нормативную продолжительность в рабочих днях (`norm_duration_days`), перечень предшествующих этапов и тип технологической связи (`predecessors`: FS — Finish-to-Start, SS — Start-to-Start), признак нахождения на критическом пути (`is_critical_path`), привязку к физическому участку (`area_name`) и текущий статус (`PLANNED`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED`). Для монолитного домостроения реализована автогенерация по МРР-3.2.81-12, для остальных типов объектов график импортируется из файлов заказчика (CSV или XLSX через `POST /api/v1/plan/objects/{id}/plan/import`). В составе репозитория предоставлены эталонные файлы-примеры графиков: `data/seed/demo_schedule.csv` и `data/seed/schedule.xlsx`.

2. **Правила соответствия «этап → техника» (`plandb.stage_rule`):**  
   Определяют нормативные требования к механизации каждого вида строительных работ:

    - `required` — перечень обязательных классов техники и их минимальное количество;
    - `allowed` — перечень разрешенной вспомогательной техники;
    - `signature` — технологическая сигнатура (набор машин или визуальная стадия), однозначно свидетельствующая о фактическом старте этапа;
    - `min_sessions` — минимальное число рабочих сессий подтверждения.

3. **Иерархический классификатор видов работ (`plandb.work_type`):**  
   Четырехуровневый справочник работ г. Москвы с кодировкой видов строительно-монтажных процессов и указанием их применимости для различных типов объектов капитального строительства.

### 1.4. Хранение информации об отклонениях и нарушениях

Контроль хода строительства осуществляется на основе **10 автоматизированных правил выявления нарушений и отклонений (D1–D10)**.

Настройки правил хранятся в таблице `analysisdb.deviation_rule` (базовая критичность, числовые пороги, условия временной эскалации и параметрические шаблоны сообщений из конфигурации `services/analysis-service/data/deviation_rules.yaml`). Все 10 правил преднастроены в системе:

| Код | Наименование правила | Условие срабатывания | Базовая критичность |
| :--- | :--- | :--- | :--- |
| **D1** | Отсутствие обязательной техники | На активном по графику этапе в течение заданного числа сессий отсутствует вся обязательная техника | `MEDIUM` (эскалация до `HIGH` через 1 день) |
| **D2** | Неполный комплект техники | На активном этапе зафиксирована лишь часть обязательной техники (не соблюден минимальный комплект) | `MEDIUM` (эскалация до `HIGH` через 3 дня) |
| **D3** | Непредусмотренная техника / опережение | На участке зафиксирована техника, не входящая в правила текущих этапов (при совпадении с будущим этапом фиксируется возможное опережение) | `MEDIUM` |
| **D4** | Необоснованный простой техники | Техника находится на площадке без движения свыше допустимого числа рабочих сессий подряд | `LOW` (эскалация до `MEDIUM` через 1 день) |
| **D5** | Техника вне целевой рабочей зоны | Машины выполняют операции за пределами разрешенной рабочей зоны объекта | `MEDIUM` |
| **D6** | Нарушение границ опасной зоны | Заезд строительной техники или нахождение людей в границах опасной зоны | `HIGH` |
| **D7** | Несоответствие визуальной стадии | Фактический внешний вид объекта по данным классификатора отстает от стадии, требуемой календарным планом | `HIGH` |
| **D8** | Затягивание сроков этапа | Плановый срок завершения этапа истек, но на площадке продолжают фиксироваться машины его сигнатуры | `HIGH` |
| **D9** | Срыв планового старта работ | Наступила плановая дата старта этапа, но в течение первых 3 рабочих дней технологическая сигнатура работ не обнаружена | `HIGH` |
| **D10** | Участок вне контроля ИИ | Наблюдение невозможно из-за внешних факторов (не размечена зона, загрязнена оптика, темнота, перекрытие обзора) | `INFO` |

Журнал зафиксированных инцидентов сохраняется в `analysisdb.deviation` со ссылками на подтверждающие фотокадры (`evidence_image_ids`), структурированными фактами нарушения в формате JSONB (`facts`), статусом жизненного цикла (`ACTIVE`, `RESOLVED`) и вердиктом ответственного инженера (`NEW`, `CONFIRMED`, `REJECTED`).

## 2. Структура кода и комментарии

### 2.1. Организация монорепозитория

Проект спроектирован в виде модульного монорепозитория со строгим разграничением сфер ответственности:

```text
ConstructionSupervision/
├── apps/
│   └── web/                # React 18 SPA (TypeScript): дашборд, интерактивная диаграмма Ганта,
│                           # лента отклонений, редактор полигональных зон и фотокамер
├── services/
│   ├── gateway/            # Nginx: единая точка входа (Reverse Proxy), раздача веб-интерфейса,
│   │                       # маршрутизация REST API, Swagger UI и объектного хранилища
│   ├── plan-service/       # Сервис плана: нормативный график СМР по МРР-3.2.81-12, WBS-шаблоны,
│   │                       # производственный календарь, технологические правила «этап → техника»
│   ├── site-service/       # Сервис площадки: камеры, полигоны зон, прием снимков, воркер
│   │                       # распознавания (site-worker на базе arq/Redis), окна наблюдений
│   ├── vision-service/     # Сервис компьютерного зрения: детекция техники и людей (YOLO-World v2),
│   │                       # классификация визуальной стадии (OpenCLIP), алгоритмическая оценка качества
│   └── analysis-service/   # Сервис анализа: правила нарушений D1–D10, расчет прогресса и CPM/SPI,
│                           # генерация PDF-отчетов с текстовым резюме локальной нейросетью
├── packages/
│   ├── contracts/          # Межсервисные спецификации: equipment_classes.yaml, enums.yaml, OpenAPI
│   ├── py-common/          # Общая Python-библиотека: логирование, аутентификация, обработка ошибок
│   └── ts-api-client/      # Автогенерируемый типизированный TypeScript-клиент для веб-интерфейса
├── ml/                     # Офлайн-модуль ML: подготовка датасетов, дообучение YOLO-World, скрипты
│                           # честной оценки качества (mAP50, матрицы ошибок) на тестах
└── scripts/                # Утилиты развертывания: загрузка весов моделей (fetch_models.py),
                            # предзаполнение демо-данных (seed.py), сквозное тестирование (e2e.py)
```

### 2.2. Архитектура микросервисов и изоляция доменной логики

Каждый микросервис бэкенда построен по принципам многослойной чистой архитектуры:

- `src/core/` — **изолированная доменная логика.** Включает чистые детерминированные функции: правила выявления нарушений (D1–D10), расчет критического пути (CPM) и показателей освоенного объема (SPI), геометрическую привязку точек к полигонам зон (Ray Casting), алгоритмическую оценку размытия кадра. Модули ядра не содержат обращений к базам данных, сетевых вызовов или системного ввода-вывода, благодаря чему на 100% покрыты быстрыми модульными тестами.
- `src/dal/` — слой доступа к данным на базе асинхронной ORM SQLAlchemy 2.0 (декларативные модели, репозитории с транзакционными границами).
- `src/api/` — транспортный слой FastAPI: роутеры, сквозная валидация схем запросов и ответов через Pydantic v2, обработчики типовых доменных исключений.
- `src/services/` — прикладные сценарии оркестрации межсервисного взаимодействия и длительных бизнес-процессов.

### 2.3. Культура комментирования кода

- Исходный код снабжен исчерпывающими комментариями и docstring-описаниями на русском языке.
- Комментарии строго ориентированы на пояснение архитектурных и инженерных причин («почему код спроектирован именно так»), а не на банальный пересказ синтаксиса.
- Все алгоритмические допущения и формулы снабжены прямыми ссылками на нормативные документы (например, нормативные сроки периодов строительства по таблице 1 МРР-3.2.81-12, формулы расчета задержки критического пути CPM).
- Заголовочные блоки модулей содержат указание функционального назначения и соответствия разделам технического задания.

## 3. Условия, ограничения и качество машинного обучения

### 3.1. Архитектура нейросетевого конвейера и используемые модели

В системе реализован специализированный многокомпонентный конвейер компьютерного зрения, исключающий взаимные блокировки и обеспечивающий автономность работы:

1. **Детектор строительной техники и персонала:**  

    - **Архитектура:** Ultralytics YOLO-World v2 (размерность small, `yolov8s-worldv2`, 35 МБ). Модель открытого словаря (open-vocabulary), в которой целевые классы задаются текстовыми промптами на английском языке из файла `packages/contracts/equipment_classes.yaml`.
    - **Базовые веса:** `yolov8s-worldv2.pt` (предобученные веса Ultralytics).
    - **Рабочие веса стенда:** `yolov8s-worldv2-ce-ulima-v1.pt` (`ce-ulima-v1`), дообученные на объединенном наборе данных строительной техники Construction Equipment и стационарных камерах 4K ЖК «Лима». Дообучение выполняется на самом формате YOLO-World, что сохраняет возможность динамического расширения классов через текстовые промпты без изменения программного кода детектора.

2. **Классификатор визуальной стадии строительства:**  

    - **Архитектура:** OpenCLIP ViT-B-32 (чекпоинт `laion2b_s34b_b79k`, файл `data/models/openclip-vit-b32/open_clip_model.safetensors`, 600 МБ).
    - **Принцип работы:** zero-shot сопоставление визуального эмбеддинга всего кадра стройплощадки с усредненными текстовыми эмбеддингами стадий строительства (котлован `PIT`, свайное поле `PILES`, фундамент `FOUNDATION`, монолитный каркас `FRAME`, фасад и кровля `FACADE`, благоустройство `LANDSCAPING`) из конфигурации `services/vision-service/data/stage_prompts.yaml`.

3. **Текстовый энкодер промптов техники:**  

    - **Модель:** OpenAI CLIP ViT-B/32 (`data/models/clip/ViT-B-32.pt`, 340 МБ). Локально преобразует текстовые описания классов техники в векторные представления для YOLO-World при старте контейнера, устраняя потребность в доступе к интернету во время работы.

4. **Алгоритмический модуль контроля пригодности снимков:**  

    - Анализ качества (`services/vision-service/src/core/quality.py`) выполняется мгновенно классическими математическими методами: расчет интегральной освещенности кадра в градациях серого и оценка степени расфокусировки по дисперсии оператора Лапласа (Laplacian variance), приведенной к калиброванной шкале. Позволяет отсекать ночные, засвеченные или загрязненные кадры без расхода ресурсов GPU.

5. **Локальная языковая модель аналитического резюме:**  

    - **Модель:** Gemma 4 E4B Instruct в формате квантования GGUF Q4_K_M (файл `data/models/llm/gemma-4-E4B-it-Q4_K_M.gguf`, 4.9 ГБ), развернутая в микросервисе `llm` на движке `llama.cpp` (серверный образ с аппаратным ускорением CUDA). Модель принимает на вход структурированные JSON-факты прогона анализа и формирует связный текст для руководителя проекта. При отсутствии ресурсов GPU или недоступности модели сервис автоматически генерирует резюме по детерминированному инженерному шаблону.

| **Тестовый набор экспертов** (`lct-test`) | 100 разнородных снимков организаторов хакатона, около 10 различных стройплощадок Москвы, лето и зима, 600 единиц строительной техники. | Независимая тестовая выборка с верифицированной ручной разметкой в LabelMe. Полностью исключена из обучения. |

#### Результаты измерений качества детекции (mAP50):

- **На отложенном тесте площадки Лима (264 кадра 4K):**
  - Базовая модель zero-shot YOLO-World v2 без дообучения: **mAP50 = 0.07** (модель путает бытовки и контейнеры с самосвалами, генерируя в среднем 8.6 ложных рамок на кадр).
  - Дообученная модель `ce-ulima-v1`: **mAP50 = 0.81** (по классам: бетоносмесители — 0.99, автобетононасосы — 0.99, самосвалы — 0.92, башенные краны — 0.87, погрузчики — 0.84; среднее число ложных детекций снижено до 0.1 на кадр).

- **На контрольной выборке организаторов (100 сложных кадров, 600 машин):**
  - Базовая zero-shot модель дает колоссальное число ложных срабатываний (**521 ложная рамка** на 100 кадров при пороге 0.35, называя столбы и конструкции сваебойными установками и кранами).
  - Дообученная модель `ce-ulima-v1` успешно подавляет ложные детекции (**всего 18 ложных рамок** против 521 у базовой модели).
  - При рабочем пороге 0.35 модель уверенно находит массовую технику, присутствовавшую в обучающих датасетах (экскаваторы — 68 верных детекций, самосвалы), обеспечивая точность Precision 0.73 по экскаваторам.
  - Ограничение: техника, специфичная для московских строек и отсутствующая в открытых датасетах с открытой лицензией (буровые сваебойные установки с тяжелыми мачтами, специализированные гусеничные краны), дообученной моделью пропускается (mAP50 = 0.00 по буровым). Это объективное инженерное ограничение текущих открытых данных, для преодоления которого система переводит нераспознанные участки в статус D10 для ручной проверки инженером.

#### Быстродействие конвейера компьютерного зрения:

- **Инференс на GPU (NVIDIA RTX 3060 Laptop):** медиана **29 мс**, 90-й перцентиль **58 мс** на снимках организаторов; **23 мс** / **53 мс** на кадрах 4K (требование технического задания: ≤ 100 мс выполняется с двукратным запасом).
- **Инференс на CPU (входное разрешение 960px):** медиана **900 мс**, 90-й перцентиль **985 мс** (требование технического задания: ≤ 1–2 с полностью соблюдено).

### 3.4. Поддерживаемые типы объектов и технологические этапы СМР

Система поддерживает 4 канонических типа объектов капитального строительства (`packages/contracts/enums.yaml`):

1. **Монолитное домостроение** (`RESIDENTIAL_MONOLITH`): преднастроен нормативный расчет сроков по МРР-3.2.81-12 и WBS-шаблон из 12 этапов наружных СМР.
2. **Панельное домостроение** (`RESIDENTIAL_PANEL`): графики с контролем монтажной техники (башенные и монтажные краны, панелевозы, длинномеры).
3. **Общественные здания** (`PUBLIC_BUILDING`): школы, детские сады, поликлиники, административные комплексы.
4. **Дорожное строительство и благоустройство** (`ROAD`): контроль дорожной техники (асфальтоукладчики, катки, грейдеры, самосвалы).

#### Импорт календарного графика из внешних файлов (CSV / XLSX)

Для панельных домов, общественных зданий и дорожного строительства (а также для индивидуальных проектов монолитных объектов) график производства работ импортируется из файлов заказчика через REST API (`POST /api/v1/plan/objects/{id}/plan/import`) либо через модальное окно веб-интерфейса (*«Построить график → Из файла CSV / XLSX»*):

- **Поддерживаемые форматы:** CSV (разделители `;` или `,`, кодировка UTF-8) и XLSX (Microsoft Excel).
- **Обязательные колонки таблицы:** `код` (`code`), `наименование` (`name`), `начало` (`start`), `окончание` (`end`).
- **Опциональные колонки:** `тип участка` (`zone_type`), `визуальная стадия` (`visual_stage`), `связи` (`predecessors`, например `10.4-10.8 FS`), `фаза` (`phase`). Пропущенные атрибуты и технологические правила техники автоматически подтягиваются из шаблонов этапов и Сводного классификатора строительных работ Москвы (`plandb.work_type`).
- **Файлы-примеры для проверки импорта в репозитории:**
    - **CSV-файл примера:** `data/seed/demo_schedule.csv` (также доступен по пути `services/plan-service/tests/fixtures/demo_schedule.csv`) — компактный пример графика со связями Finish-to-Start;
    - **XLSX-файл примера:** `data/seed/schedule.xlsx` — полноразмерный демонстрационный график СМР с привязкой зон и фаз.

Все 10 правил автоматического контроля нарушений (D1–D10) применяются универсально ко всем типам объектов независимо от способа формирования графика.

### 3.5. Ограничения системы

- **Неблагоприятные погодные условия и оптические помехи:** Кадры, снятые в условиях нулевой видимости (ночь без прожекторов), плотного тумана или сильного загрязнения защитного стекла камеры, автоматически идентифицируются модулем качества (`services/vision-service/src/core/quality.py`). Данные участки переводятся в статус D10 («Вне контроля ИИ»), блокируя появление ложных отклонений и уведомляя оператора о необходимости проверки.
- **Обезличивание и защита персональных данных:** В соответствии с требованиями законодательства РФ система не осуществляет распознавание лиц граждан и государственных регистрационных знаков транспортных средств. В базу данных сохраняются исключительно обезличенные категории техники и координаты ограничивающих прямоугольников.

## 4. Инструкция по сборке, установке и запуску решения

Решение развертывается в изолированных Docker-контейнерах под управлением Docker Compose.

---

### 4.1. Системные требования

- **Операционная система:** Linux (Ubuntu 22.04 LTS и новее) либо Windows 10/11 с установленным Docker Desktop (режим WSL2).
- **Процессор и память:** не менее 4 процессорных ядер, от 16 ГБ оперативной памяти (ОЗУ).
- **Дисковое пространство:** не менее 35 ГБ свободного пространства на SSD-накопителе (для размещения образов контейнеров, весов нейросетей, базы данных и демо-снимков).
- **Графический ускоритель (опционально):** видеокарта NVIDIA (от 6 ГБ VRAM) с установленным NVIDIA Container Toolkit для аппаратного ускорения инференса.

---

### 4.2. Пошаговый запуск (быстрый старт)

#### Шаг 1. Клонирование репозитория и создание файла конфигурации

```bash
git clone <URL_РЕПОЗИТОРИЯ>
cd ConstructionSupervision
cp .env.example .env
```
*(Для командной строки Windows PowerShell: `copy .env.example .env`)*

---

#### Шаг 2. Загрузка весов моделей и демонстрационных данных

Скрипт `scripts/fetch_models.py` выполняет потоковую загрузку недостающих бинарных компонентов со сверкой контрольных сумм SHA-256. Загрузка производится во временные файлы `.part`, предотвращая появление поврежденных данных при обрыве соединения:

```bash
docker compose run --rm tools python scripts/fetch_models.py
```
*(При наличии локального интерпретатора Python: `python scripts/fetch_models.py`)*

Что именно скачивает скрипт:

- **Группа `models` (базовые веса vision-service в `data/models/`):**
    - `yolov8s-worldv2.pt` (35 МБ) — базовая модель детекции техники Ultralytics YOLO-World v2;
    - `openclip-vit-b32/open_clip_model.safetensors` (600 МБ) — модель OpenCLIP ViT-B-32 для классификации визуальной стадии объекта;
    - `clip/ViT-B-32.pt` (340 МБ) — текстовый энкодер OpenAI CLIP для кодирования словаря промптов детектора.
- **Группа `demo` (ассеты демонстрационного стенда):**
    - `yolov8s-worldv2-ce-ulima-v1.pt` (35 МБ) — дообученный детектор техники на строительных датасетах (указан в `VISION_DET_WEIGHTS`);
    - `demo-images.zip` (56 хронологических кадров 4K стационарных камер площадки Лима, распаковываются в `data/seed/images/`).
- **Группа `llm` (локальная языковая модель):**
    - `gemma-4-E4B-it-Q4_K_M.gguf` (4.9 ГБ) — квантованная модель Gemma 4 E4B instruct для контейнера `llm` (llama.cpp).

*Полезные флаги скрипта:*

- `--skip llm` — не скачивать модель Gemma (экономия 5 ГБ трафика, если резюме формируется шаблонизатором или внешним API);
- `--skip demo` — не скачивать демонстрационные кадры и дообученные веса;
- `--force` — принудительно перезакачать все файлы заново.

---

#### Шаг 3. Запуск контейнеров приложения

- **Стандартный запуск в режиме CPU (подходит для любых систем):**

  ```bash
  docker compose up -d
  ```

- **Запуск с аппаратным ускорением GPU (видеокарта NVIDIA):**

  ```bash
  docker compose -f docker-compose.yml -f docker-compose.gpu.yml up -d
  ```

---

#### Шаг 4. Проверка готовности сервисов

Скрипт проверяет эндпоинты `/health/ready` всех микросервисов и сводный статус шлюза:

```bash
docker compose run --rm tools python scripts/health.py
```

Все компоненты (`postgres`, `s3`, `redis`, `plan-service`, `site-service`, `site-worker`, `vision-service`, `analysis-service`, `gateway`) должны вернуть код готовности `UP` (код возврата 0).

---

#### Шаг 5. Загрузка демонстрационного сценария

Скрипт инициализирует демонстрационный объект капстроительства, импортирует нормативный график СМР, настраивает геометрию рабочих зон камер и загружает хронологию снимков за три последовательных дня:

```bash
docker compose run --rm tools python scripts/seed.py
```

---

#### Шаг 6. Сквозная верификация системы (E2E-тест)

Запуск автоматического теста сквозного контура:

```bash
docker compose run --rm tools python scripts/e2e.py
```

Тест автоматически проверяет факт выявления всех 7 расчетных инцидентов сценария, соответствие планового и фактического индексов освоенного объема SPI, а также корректность формирования итогового PDF-отчета.
