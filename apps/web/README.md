# web — интерфейс оператора

## 1. Назначение

Единственный интерфейс системы: дашборд объекта, диаграмма Ганта план-факт, лента
предупреждений с доказательствами, просмотр камер, редакторы графика, правил и зон,
отчёты.

Интерфейс — это витрина методики. Пользователь должен за десять секунд понять,
**что не так, где именно и почему система так решила**.

## 2. Стек

| Что | Выбор | Почему |
| :--- | :--- | :--- |
| Язык и сборка | TypeScript 5 (`strict`), Vite | Быстрая сборка, типы от API «из коробки» |
| UI | React 18 + Tailwind | Скорость разработки, единообразие без дизайн-системы |
| Данные | TanStack Query | Кэш, инвалидация, повторы — бесплатно |
| Клиент API | `packages/ts-api-client`, генерируется из OpenAPI | Контракт нельзя нарушить незаметно |
| Гант | Свой SVG-компонент (`features/gantt`), без библиотеки | 12–30 вех, связи и перетаскивание — ~300 строк; зависимость не окупается (ниже) |
| Работа с кадром | `canvas` / SVG поверх изображения | Рамки детекций и редактор полигонов зон |
| Формы | `react-hook-form` + `zod` | Валидация на клиенте по схеме |

**Гант — без библиотеки** (решение T32, 26.09). Критерии были: перетаскивание дат, связи между
вехами, приемлемый вид при 15–30 вехах. Готовые компоненты дают это, но рисуют свою модель
задачи: у нас на той же строке нужны плановое окно, заливка прогресса цветом статуса,
фактический старт и прогнозный хвост из другого сервиса, а даты — рабочие дни календаря
объекта. Подгонять чужую модель дольше, чем нарисовать SVG: геометрия — чистые функции
`features/gantt/layout.ts`, перетаскивание — те же pointer-события, что в редакторе зон.
Зависимость и её вес в образе не нужны (AGENTS.md, §6).

## 3. Экраны

| Экран | Маршрут | Содержание | Данные | Приоритет |
| :--- | :--- | :--- | :--- | :--- |
| **Объекты** | `/objects` | Список объектов, статус, задержка, число отклонений | plan + analysis | Must |
| **Дашборд** | `/objects/:id` | Статус («в графике / отставание N дней»), SPI, уверенность, счётчики отклонений по серьёзности, вехи в риске, слепые участки, последние снимки | `analysis/objects/{id}/status`, `/progress` | Must |
| **Предупреждения** | `/objects/:id/deviations` | Лента карточек: текст, веха, зона, правило, числа, снимки с рамками, кнопки «подтвердить / ложное»; фильтры по коду, серьёзности, периоду | `analysis/deviations`, `/explain`, `site/images/{id}/annotated` | Must |
| **Гант** | `/objects/:id/gantt` | Плановые полосы, фактический старт, прогнозное окончание, критический путь, зависимости; перетаскивание дат с пересчётом | `plan/objects/{id}/plan` + `analysis/objects/{id}/progress` | Must |
| **Камеры** | `/objects/:id/cameras` | Снимок с наложенными зонами и рамками, статус каждой машины, переключение по времени и камерам | site | Must |
| **Загрузка** | `/objects/:id/upload` | Пакетная загрузка снимков, разбор результата, ручной ввод времени для `NEEDS_TIME` | `site/images` | Must |
| **Настройки** | `/objects/:id/settings/*` | Импорт и генерация графика, редактор вех, **редактор правил «веха → техника»**, классы техники, пороги отклонений | plan + analysis | Should |
| **Отчёты** | `/objects/:id/reports` | Формирование PDF, история отчётов, LLM-резюме с пометкой источника | `analysis/reports`, `analysis/summary` | Should |
| **Редактор зон** | `/objects/:id/settings/zones` | Разметка полигонов поверх эталонного кадра | site | Could |
| **Лента этапов** | компонент дашборда | Компактная полоса вех в одну строку (п. 3.1) | те же данные, что у Ганта | Could |

Главный экран — **предупреждения**, а не дашборд. Там видно то, за что нас оценивают
в первую очередь: правило, числа и снимок-доказательство. Дашборд — витрина,
лента предупреждений — доказательство.

**Порядок сокращения, если поджимает время:** сначала отчёты, затем редактор зон
(дорогой, даёт мало — зоны в MVP приходят из `data/seed/cameras.json`, интерфейс их
только отрисовывает), затем Гант упрощается до статичного, без перетаскивания.
**Редактор правил резать нельзя:** демонстрация «меняем правило в UI, отклонение
исчезает» — это доказательство архитектурного критерия, заменить её нечем.

Что уже реализовано, видно по [docs/board.md](../../docs/board.md). Статика собирается в
образ gateway, поэтому `make up` отдаёт SPA.

Рамки детекций и полигоны зон рисуются в интерфейсе SVG-слоем поверх снимка: сервер готовых
«кадров с рамками» не делает. Снимок открывается по presigned-ссылке из `GET /site/images/{id}`,
рамки берутся из того же ответа, а зоны камеры — из `GET /site/zones?camera_id=`. viewBox слоя —
в пикселях кадра (`shared/ui/Frame.tsx`): при растягивании 0…1 на неквадратный кадр круги
вершин стали бы эллипсами.

**Предупреждения** (`features/deviations`): слева лента по дням начала эпизода, справа
карточка выбранного отклонения. В карточке текст вывода, группы обязательной техники с нормой
и наблюдением, ключевые числа из `facts`, настройки правила, снимок-доказательство с рамками из
вывода и зоной участка, проверенные сессии из `/explain` и вердикт оператора с комментарием.
Фильтры (статус, код, серьёзность, период) и выбранная карточка — в адресе
(`?status=open&code=D2&id=`), ссылку на карточку можно переслать. Счётчики серьёзности на
дашборде ведут в ленту с фильтром. Разбор `facts` и сессий — `entities/deviation.ts`: их
состав зависит от кода, поэтому поля читаются с проверкой типа.

**Правила «веха → техника»** (`features/rules-editor`, `/objects/:id/settings/rules`): слева вехи
объекта, справа правило выбранной (веха — в адресе, `?stage=`). Правятся группы «любой из» с
минимумом, допустимая техника, сигнатура старта со стадией по фото, `min_sessions` и включение;
у вехи без правила оно создаётся. Правки копятся в черновике (`rules-editor/draft.ts`, чистый
редьюсер), пустая группа и пустое правило не сохраняются. «Сохранить и пересчитать» — PATCH
правила, затем прогон анализа с ожиданием: экран показывает, какие отклонения исчезли из ленты
и какие появились (сравнение ленты до и после по id, а не статистика прогона — plan-service
мог пересчитать объект по своему сигналу раньше).

**Гант** (`features/gantt`, `/objects/:id/gantt`): слева вехи по `seq`, справа сетка по дням.
Полоса — плановое окно (критический путь — цветом акцента), внутри — выполненная доля цветом
статуса вехи, треугольник — фактический старт, пунктирный хвост — прогноз позже плана, черта —
прогноз раньше, `±N` — отставание в рабочих днях. Стрелки — связи FS/SS/FF/SF, пунктир —
момент анализа. Масштаб: весь график по ширине экрана, месяцы, недели. Щелчок по вехе открывает
карточку (веха — в адресе, `?stage=`): план, норма и основание срока, резерв или «на
критическом пути», предшественники, факт, прогноз и откуда прогресс — по плану (с причиной) или
по наблюдениям. Вехи в риске на дашборде ведут на свою карточку.

Даты вехи правятся формой в карточке или перетаскиванием полосы: целиком — длительность в
рабочих днях сохраняется, за край — меняется начало или конец; края прилипают к рабочим дням
календаря объекта (`gantt/workdays.ts`, выходные и праздники из `GET /plan/objects/{id}/plan`).
Пока даты в черновике, исходное окно видно пунктиром, а прогнозный хвост скрыт: он посчитан по
старым датам. «Сохранить и пересчитать» — `PATCH /plan/stages/{id}`, прогон анализа с
ожиданием, затем «было → стало»: прогноз и отставание вехи, критический путь, статус и
отставание объекта.

**Камеры** (`features/cameras`): вкладки камер, снимки по дням и времени, кадр с зонами и
рамками, у каждой машины — участок, к которому её отнёс site, и сдвинулась ли она с прошлого
окна. Классы на кадре можно скрывать: людей на обзорной камере десятки. Любой снимок можно
сделать эталонным кадром камеры. Камера и снимок — в адресе (`?camera=&image=`).

**Отчёты** (`features/reports`, `/objects/:id/reports`): форма периода и список готовых PDF.
Период по умолчанию — неделя по день момента анализа (по Москве), как у analysis-service: отчёт
оформляет посчитанные выводы. «Сформировать PDF» ждёт ответа (~2 с на демо) и показывает ссылку,
число вставленных и невставленных снимков-доказательств и источник резюме (шаблон или
нейросеть). Без анализа форма не показывается: формировать нечего. Кнопка «Отчёты» — на
дашборде.

**Редактор зон** (`features/zones-editor`): полигоны на эталонном кадре камеры. Вершины
тянутся мышью, «+» на середине ребра добавляет вершину, двойной щелчок удаляет, внутренняя
часть двигает зону целиком; новая зона рисуется щелчками по углам. Тип участка — с подсказкой
его роли, название — с подсказками из участков других камер и строкой «тот же участок, что
на камере …». Слой «где стояла техника» показывает точки контакта машин со всех снимков
камеры: по ним видно, где проводить границу. Правки копятся в черновике
(`zones-editor/draft.ts`, чистый редьюсер) и уходят одной кнопкой: каждое сохранение зоны
ставит пересчёт фактов всех окон объекта, и сохранять на каждое движение вершины незачем.
Разметку демо-объекта в `data/seed/cameras.json` переносит `python scripts/export_zones.py`.

### 3.1. Лента этапов (`StageTimeline`) — необязательная

**Календарный график показывает Гант, он же закрывает требование F10.** Лента —
необязательная компактная надстройка: та же информация в одну строку, всегда на виду
на дашборде, без перехода на отдельный экран. Делается только если Гант готов
и осталось время; спецификация ниже сохранена, чтобы не проектировать заново.

Компактная горизонтальная полоса всех вех объекта в календарном масштабе. Стоит
на дашборде сразу под шапкой со статусом.

Что на ленте:

- вехи слева направо, ширина сегмента пропорциональна плановой длительности;
- ось дат сверху и **маркер «сегодня»** вертикальной линией;
- заливка сегмента по статусу вехи: `NOT_STARTED`, `IN_PROGRESS`, `DONE`, `LATE`, `AHEAD`;
- отметка фактического старта и пунктирный «хвост» прогнозного окончания там,
  где прогноз выходит за плановую дату;
- вехи критического пути выделены, у остальных резерв показан светлее;
- под сегментом — плановые даты; при нехватке ширины остаются только те,
  что помещаются без наложения.

Поведение: наведение — всплывающая подсказка с плановыми датами, фактическим стартом,
прогрессом, SPI, прогнозом, задержкой и числом открытых отклонений; клик по вехе —
переход в ленту предупреждений с фильтром по этой вехе.

Новых эндпоинтов не нужно: лента живёт на тех же двух запросах, что и Гант —
`plan/objects/{id}/plan` (названия, порядок, плановые даты, критический путь) и
`analysis/objects/{id}/progress` (фактический старт, статус, прогноз, задержка).

Чем отличается от Ганта: лента — одна строка, отвечает только на вопрос «где мы
сейчас». Гант — многострочная сетка, и он умеет то, чего лента не умеет: показывать
зависимости между вехами и править даты перетаскиванием. Поэтому Гант обязателен,
а лента нет.

Состояния: плана нет — «график не сгенерирован» с кнопкой генерации; фактов нет —
показываем только плановые сегменты серым, без прогноза.

```text

│   ├── api/        # обёртка над сгенерированным клиентом, перехват ошибок
│   ├── ui/         # переиспользуемые компоненты
```

## 5. Правила

- `any` запрещён; типы ответов API — только из `packages/ts-api-client`, дублировать нельзя.
- Компонент отображает, хук считает: агрегации и форматирование — вне JSX.
- Серверное состояние — только TanStack Query; `useState` — для состояния интерфейса.
- Интерфейс только на русском, поэтому строки экрана можно писать прямо в JSX.
  В `shared/locale/ru.ts` живут общие строки: названия перечислений (статусы, серьёзность, коды
  отклонений), тексты ошибок, подписи единиц измерения.
- **Три состояния обязательны на каждом экране:** загрузка, пусто, ошибка. Пустой экран
  без объяснения — дефект.
- Ошибка API показывается пользователю тем `message`, который вернул сервис, плюс
  `request_id` мелким шрифтом: на демо это экономит минуты.
- Числа всегда с единицей измерения и с пояснением происхождения. Прогноз сопровождается
  уровнем уверенности и оговоркой «при сохранении текущего темпа».
- Слепые участки показываются явным предупреждением «участок вне контроля ИИ — проверить
  вручную», а не пустотой.

## 6. Взаимодействие с API

Все запросы идут на тот же адрес, откуда отдан интерфейс (`/api/v1/...`) — gateway
проксирует. Заголовок `X-API-Key` подставляется обёрткой в `shared/api`.

После изменения контракта на бэкенде: `make contracts` → типы обновляются →
несоответствия падают на этапе сборки, а не на демо.

Типы подключаются алиасом `@api` (`packages/ts-api-client/src`, по пространству имён на
сервис), короткие имена схем — `src/shared/api/schemas.ts`: `PlanSchema<"ObjectRead">`.
Образ gateway копирует сгенерированные типы рядом с `apps/web`, как в репозитории.

## 7. Запуск

```bash
# в составе стека (собранная статика отдаётся gateway)
make up                       # http://localhost:8080

# разработка с hot-reload
cd apps/web && npm install && npm run dev    # http://localhost:5173, проксирует /api на gateway
```

## 8. Допущения и ограничения

- Одна роль пользователя: разграничения прав нет ([ADR-0010](../../docs/decisions/0010-auth.md)).
- Интерфейс рассчитан на десктоп; на планшете работает, мобильная вёрстка не оптимизировалась.
- Реального времени нет: данные обновляются по запросу и по таймеру (сессия — 30 минут,
  чаще не требуется).
- Локализация только русская.
- **Кнопка «Пересчитать» на дашборде считает на тот же `as_of`, что у показанного статуса:**
  она отвечает на вопрос «что изменилось после правки настроек» и не сдвигает момент анализа.
  Без статуса момент выбирает analysis-service.
- **Список объектов запрашивает статус каждого объекта отдельно** (`/analysis/objects/{id}/status`):
  на стенде объектов единицы. `OBJECT_NOT_ANALYZED` — не ошибка, а «анализа ещё не было».
- **Последние снимки** — хвост `GET /site/images` по времени съёмки (список отдаётся по
  возрастанию) и карточки снимков ради presigned-ссылок.
- **Камера показывает последние 200 снимков** (предел страницы API). Больше — экран говорит,
  сколько не показано.
- **Статуса машины «работает / простой» на экране камер нет:** его считает analysis-service по
  сериям окон, а site отдаёт только участок и сдвиг. Статус виден в карточке отклонения.
- **Слой «где стояла техника» грузит карточку каждого снимка камеры** — до 200 запросов. Он
  включается по запросу и нужен при разметке, а не в работе.
- **Вердикт ставится и закрытому отклонению:** статус остаётся «Закрыто», вердикт показывается
  рядом (поле `verdict`, methodology.md, раздел 9, правило 3).
- **Лента показывает до 200 отклонений** (предел страницы API) и говорит, сколько не показано.
- **Период фильтра — сутки по Москве** (UTC+3 без летнего времени); API ищет эпизоды,
  пересекающиеся с периодом.
- **Кто поставил вердикт** — заголовок `X-Actor` из `VITE_ACTOR` (по умолчанию «оператор»):
  ролей и входа нет (ADR-0010).
- **Линия «на момент анализа» — сутки `as_of` по Москве**, а не сегодняшняя дата: демо-хронология
  датирована графиком (октябрь 2026), и «сегодня» стояло бы вне наблюдений.
- **Резерв вехи на Ганте — числом из plan-service**, полосой не рисуется: он в рабочих днях, и
  перевод в календарные на клиенте повторил бы CPM.
- **Правка дат вехи не сдвигает соседей:** plan-service пересчитывает только резервы, и
  нарушенная связь видна отрицательным резервом в карточке вехи. Каскадный сдвиг — решение
  планировщика, а не интерфейса.
- **Нерабочий день в форме дат не сохраняется** — экран говорит, какая дата на выходной или
  праздник; plan-service такие даты принял бы, но CPM считает по рабочим дням.
- **Ссылки на PDF живут час** (`S3_PRESIGN_TTL_S`): список отчётов считается устаревшим через
  5 минут и перечитывается при возврате на вкладку, так что ссылка на экране свежая.
- **Правки зон не блокируются между вкладками:** две вкладки редактора одной камеры сохранят
  последнюю правку. На стенде оператор один.
