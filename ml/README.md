# ml — обучение моделей (офлайн)

Каталог **не является сервисом** и не участвует в продуктовом контуре. Здесь живут
датасеты, обучение, экспорт весов и оценка качества. `vision-service` получает готовые
веса из `data/models/` и про этот каталог ничего не знает.

**Дообучение оказалось обязательным.** Замысел был такой: система работает из коробки на
open-vocabulary детекторе, а дообучение только улучшает. Проверка на размеченных кадрах
стройки это опровергла. На отложенном тесте датасета Лимы zero-shot YOLO-World v8s даёт mAP50
0,07: бытовки и контейнеры он называет самосвалами, а погрузчик и бетононасос не находит вовсе.
YOLOE-26 s и m на тех же кадрах не лучше. Дообученный YOLO-World даёт 0,77
([docs/metrics.md](../docs/metrics.md)). Дообучается сам YOLO-World: классы по-прежнему
задаются промптами, и vision-service получает новые веса без правки кода.

Раздел 0 ниже описывает исходный план для снимков организаторов, где своей разметки нет.
Для Лимы авторазметка не понадобилась: рамки поставляются с датасетом.

## 0. Почему гибрид, а не разметка с нуля

Дорого не обучение, а разметка. На RTX 3060 обучение YOLO11s на 400 кадрах занимает
20–40 минут, а ручная разметка этих же 400 кадров — 6–8 часов человека. Поэтому:

1. **Авторазметка.** Grounding DINO или YOLO-World размечает архив организаторов;
   на GPU это минуты.
2. **Проверка руками.** Человек правит и отбраковывает рамки — примерно 1.5–2 часа
   вместо шести. Это единственный обязательный ручной шаг.
3. **Дообучение** YOLO11s на проверенной выборке — полчаса.
4. **Подмена весов** переменной `VISION_DET_WEIGHTS`. Код не меняется, сервис
   перезапускается.

Прервались после шага 1 — остаётесь на zero-shot, и это рабочее состояние,
а не поломка.

## Таксономия и маппинг

Целевые классы — те же, что в `packages/contracts/equipment_classes.yaml`: это единственный
источник классов для всей системы ([ADR-0014](../docs/decisions/0014-equipment-classes-file.md)).
Метки внешних датасетов приводятся к ним через поле `aliases` того же файла: при сведении
датасета его метки дописываются туда, а не в отдельный конфиг. vision-service берёт из этого
файла поле `prompts`. **Названия классов не хардкодятся нигде.**

Метрики считаются одинаково для обоих режимов — zero-shot и дообученного, — и в
документацию идут обе колонки. Это честно показывает, что дало дообучение.

## Датасет Лимы

[Dataset on object identification training in a construction site](https://doi.org/10.26439/ulima.datasets.13359),
Universidad de Lima, CC BY 4.0; описание — [Data in Brief, 2022](https://pmc.ncbi.nlm.nih.gov/articles/PMC8933580/).
1046 кадров 3840×2160 с четырёх неподвижных камер одной стройки (ноябрь 2020 — февраль 2021),
рамки YOLO восьми классов. Это единственный найденный открытый набор, где одна площадка снята
с нескольких неподвижных точек в разные дни, поэтому он годится и для обучения, и для демо.

**Камеры** (по подписи на кадре): `cam-torre-h` — обзорная с высоты, 8 серий за 5 дней;
`cam-i1` — с земли, 2 дня; `cam-d3` — 4 дня, 20.11 снят другой ракурс; `cam-d1` — вблизи, 3 дня.
Ракурс каждой камеры между днями расходится не больше чем на 2–3 % кадра (проверено
сопоставлением ключевых точек), кроме `cam-d3` 20.11. Серия — это около 5 минут съёмки, кроме
Torre H 22.01 (08:36–11:10).

**Классы.** Метки приведены к кодам системы через `aliases` «ulima:…». Две метки неочевидны,
обе проверены по вырезкам: `Skid_steer` (мини-погрузчик) → `loader`; `Truck_crane` →
`concrete_pump`, потому что под этой меткой размечены стрела бетононасоса и мачта бетоновода,
а не автокран. Одна рамка `Truck_crane` на кадре 726 — башенный кран, она исключена.

**Разбиение по сериям**, а не по кадрам ([prepare/ulima.yaml](prepare/ulima.yaml)): соседние
кадры серии почти одинаковы. В обучении 720 кадров, в валидации 62, в тесте 264 (все четыре
камеры).

| Класс | train | val | test |
| :--- | ---: | ---: | ---: |
| dump_truck | 198 | 2 | 64 |
| loader | 167 | 52 | 116 |
| concrete_mixer | 106 | 0 | 6 |
| concrete_pump | 125 | 10 | 20 |
| truck | 179 | 52 | 47 |
| excavator | 3 | 0 | 0 |
| tower_crane | 1779 | 183 | 731 |
| person | 15576 | 1614 | 3961 |

**Ограничения, которые надо называть жюри.**

- Одна площадка, Лима, лето, день. Ни зимы, ни ночи, ни московской застройки: на снимках
  организаторов (`lct-raw`) качество дообученной модели не измерено.
- Экскаватора почти нет (3 рамки). Дообучение его не учит, а может и ослабить.
- Миксер в тесте — 6 кадров одной серии. Число по нему — ориентир, а не метрика.
- Демо-хронология собирается из кадров той же площадки, в том числе из обучающих серий. Демо
  показывает работу системы, а качество распознавания показывает только тест.

## Обучение и оценка

torch и Ultralytics есть только в образе vision-service, поэтому всё запускается в разовом
контейнере из него. На время обучения vision-service лучше остановить: 6 ГБ видеопамяти на двоих
не хватит.

```bash
docker compose stop vision-service
IMAGE=$(docker compose config --format json | jq -r '.services["vision-service"].image')
docker run --rm --gpus all --ipc=host -v "${PWD}:/repo" -v "${PWD}/data/models:/models" -w /repo \
  --entrypoint python "$IMAGE" ml/training/train.py \
  --model /models/yolov8s-worldv2.pt --data ml/datasets/external/ulima/data-world.yaml --name world-s-ulima-v3
docker run ... ml/eval/evaluate.py --weights ml/runs/world-s-ulima-v3/weights/last.pt \
  --data ml/datasets/external/ulima/data-world.yaml --split test
cp ml/runs/world-s-ulima-v3/weights/last.pt data/models/yolov8s-worldv2-ulima-v3.pt
# в .env: VISION_DET_WEIGHTS=/models/yolov8s-worldv2-ulima-v3.pt, затем поднять vision-service
```

Дообучается сам YOLO-World, а не обычный YOLO. Имена классов в `data-world.yaml` — первые
промпты **всех** классов системы, и после обучения словарь по-прежнему задаётся промптами из
`equipment_classes.yaml`. vision-service получает веса через `VISION_DET_WEIGHTS` без правки
кода. Обычный YOLO26 или YOLO11 потребовал бы другого адаптера детектора.

**Как пришли к v3.** Все три прогона — 40 эпох (у v1 — 16), вход 1280, батч 4, около
30 минут на RTX 3060 Laptop:

- **v1** остановился на 16-й эпохе ранней остановкой с «лучшей» 1-й: метрика валидации из
  62 кадров шумит. Поэтому ранняя остановка выключена, и берутся `last.pt`, а не `best.pt`.
- **v2**: в словаре обучения были только 8 классов из датасета. В сервисе 46 погрузчиков из 116
  получили класс `bulldozer`: на промпт «bulldozer» модель не учили не срабатывать.
- **v3**: в словаре все 15 классов, отсутствующие служат отрицательными примерами. Путаница
  с бульдозером ушла.

Между v2 и v3 выбирали по валидации в условиях сервиса: 51 верная рамка против 30, ложных 26
против 59. Тест для выбора не использовался.

## Снимки организаторов

100 снимков в `datasets/lct-raw/`: фото хода строительства около десятка объектов за 2023–2026 годы,
лето и зима, разные стадии. Это главный кандидат в `lct-test`. Он разнообразен ровно в том,
что проверяют эксперты, и не пересекается с открытыми датасетами. Разметка рамок — задача H5
в [docs/board.md](../docs/board.md). Если снимки идут и в `lct-train` (после авторазметки),
разбиение делается по объектам, а не по кадрам. Иначе один объект окажется и в обучении, и в
тесте, и метрики будут завышены.

Проблемные места, известные заранее:

- `truck` против `dump_truck` — самая частая путаница; разводится разметкой и порогом;
- башенный кран и бетононасос слабо представлены в открытых датасетах — добираются
  авторазметкой zero-shot детектором с обязательной ручной проверкой;
- ночь и зима — отдельная подвыборка, иначе метрики будут красивыми и бесполезными.

## Собственный тестовый набор

Скрытого набора у организаторов нет: эксперты смотрят **наши** примеры. Поэтому
`lct-test` собирается осознанно и обязан содержать: день, ночь, сумерки; лето, зиму,
дождь; разные стадии объекта; перекрытия машин; частично невидимые зоны.

Набор **не пересекается** с обучающим. Пересечение — это подделанные метрики.

## Метрики

```bash
python ml/eval/evaluate.py --weights data/models/yolov8s-worldv2.pt --data <набор>/data-world.yaml
python ml/eval/evaluate.py --weights data/models/yolov8s-worldv2-ulima-v3.pt --data <набор>/data-world.yaml
```

Результат — таблица precision / recall / mAP50 по классам и матрица ошибок.
Оформляется в `docs/metrics.md` с указанием размера выборки и условий съёмки.

**Не измерено — так и пишем «не измерено».** Придуманная метрика в презентации — это
провал на первом же вопросе жюри.

## Экспорт весов

Экспорт в ONNX не делается: у YOLO-World при экспорте словарь запекается внутрь весов,
и классы перестают быть данными (services/vision-service/README.md, раздел 8). Веса
кладутся в `data/models/` как есть.

Веса версионируются именем файла (`yolov8s-worldv2-ulima-v3.pt`), версия попадает в ответ
`vision-service` и сохраняется в каждой детекции — вывод остаётся воспроизводимым.

## Что в git не хранится

Датасеты, веса, логи обучения, чекпоинты. В репозитории — только конфиги, скрипты
и метрики. Веса скачиваются командой `python scripts/fetch_models.py` (`make models`).
